\section{Dasar Teori}
\subsection{MySQL}

\par MySQL adalah sistem manajemen basis data relasional (RDBMS) yang menggunakan Structured Query Language (SQL) untuk melakukan definisi skema, manipulasi data, dan query. MySQL menerapkan arsitektur client--server, di mana proses server (\texttt{mysqld}) menyimpan serta mengelola data, sedangkan klien (misalnya \texttt{mysql}) digunakan untuk terhubung dan mengeksekusi perintah SQL. Dalam praktik pengembangan aplikasi, MySQL banyak dipakai karena performanya baik, dukungan ekosistem luas, serta ketersediaan dokumentasi yang lengkap \cite{mysql-refman}.

\par Pada sisi administrasi sistem, konfigurasi MySQL umumnya dilakukan melalui berkas konfigurasi (misalnya \texttt{mysqld.cnf} di Linux atau \texttt{my.ini} di Windows) untuk mengatur parameter layanan seperti port, direktori data, serta kebijakan akses jaringan melalui \texttt{bind-address}. Selain itu, MySQL memiliki mekanisme autentikasi dan hak akses (privileges) untuk memastikan hanya user tertentu yang dapat mengakses database sesuai perannya \cite{mysql-refman}.

\subsection{REST API}
\par REST API atau \textit{Representational State Transfer Application Programming Interface} adalah antarmuka pemrograman aplikasi yang mengikuti prinsip-prinsip arsitektur REST. REST sendiri diperkenalkan oleh Roy Fielding sebagai gaya arsitektur untuk sistem hipermedia terdistribusi, dan kemudian menjadi salah satu pendekatan yang paling banyak digunakan dalam pengembangan layanan web modern \cite{ibm-rest-api,restfulapi-rest}. Pada pendekatan ini, data dan fungsi dipandang sebagai \textit{resource} yang diidentifikasi melalui URI, lalu diakses atau dimanipulasi menggunakan antarmuka yang seragam. Karena sifatnya ringan, fleksibel, dan mudah diintegrasikan dengan berbagai bahasa pemrograman serta format data, REST API banyak digunakan untuk pertukaran data antara frontend, backend, layanan web, maupun database \cite{ibm-rest-api}.

\par Sebuah REST API yang baik dibangun berdasarkan sejumlah kendala arsitektural utama, yaitu \textit{uniform interface}, \textit{client-server}, \textit{stateless}, \textit{cacheable}, \textit{layered system}, dan \textit{code on demand} sebagai sifat opsional \cite{ibm-rest-api,restfulapi-rest}. Prinsip \textit{client-server} menekankan pemisahan tanggung jawab antara sisi klien dan sisi server, sehingga antarmuka pengguna dapat berkembang secara independen dari logika dan penyimpanan data di server. Sementara itu, sifat \textit{stateless} mengharuskan setiap request membawa seluruh informasi yang dibutuhkan untuk diproses, tanpa bergantung pada sesi yang disimpan di server. Pendekatan ini membuat REST API lebih sederhana, mudah diskalakan, dan lebih cocok digunakan pada arsitektur sistem terdistribusi \cite{ibm-rest-api,restfulapi-rest}.

\par Dalam implementasinya, REST API sangat sering berjalan di atas protokol HTTP, walaupun REST dan HTTP bukanlah hal yang sama \cite{restfulapi-rest}. Pada praktik umum, method HTTP seperti \texttt{GET}, \texttt{POST}, \texttt{PUT}, dan \texttt{DELETE} digunakan untuk mendukung operasi \textit{create}, \textit{read}, \textit{update}, dan \textit{delete} pada resource. Data hasil pertukaran biasanya direpresentasikan dalam format JSON karena mudah dibaca oleh manusia maupun mesin, serta bersifat independen terhadap bahasa pemrograman \cite{ibm-rest-api}. Selain itu, request dan response juga memanfaatkan header, parameter, serta status code HTTP untuk menyampaikan metadata, otorisasi, keberhasilan proses, maupun informasi kesalahan. Oleh karena itu, REST API sangat sesuai digunakan pada praktikum ini karena memudahkan komunikasi antara backend di server VPS dan frontend di komputer host.

\subsection{API Authentication}

\par \textit{API authentication} adalah proses untuk memverifikasi identitas pihak yang melakukan request ke sebuah API, sehingga server dapat memastikan bahwa request benar-benar berasal dari pengguna atau client yang sah. Pada praktiknya, autentikasi pada REST API umumnya tidak menggunakan sesi yang disimpan di server (\textit{stateless}), melainkan menggunakan kredensial yang dikirim pada setiap request melalui header HTTP.

\par Salah satu pendekatan yang banyak digunakan adalah autentikasi berbasis token, di mana server mengeluarkan token setelah proses login berhasil, lalu token tersebut digunakan kembali pada request berikutnya. Token akan menjadi bukti autentikasi, sedangkan aturan akses (misalnya berdasarkan role) dapat diterapkan sebagai bagian dari proses otorisasi setelah token diverifikasi.

\par JSON Web Token (JWT) merupakan standar token berbasis JSON yang bersifat ringkas dan aman untuk ditransmisikan, serta digunakan untuk merepresentasikan klaim (\textit{claims}) antar pihak. JWT umumnya memiliki tiga bagian utama, yaitu \textit{header}, \textit{payload}, dan \textit{signature} (format \texttt{header.payload.signature}). Signature digunakan untuk memastikan integritas token, sehingga payload tidak dapat diubah tanpa mengetahui kunci penandatanganan \cite{rfc7519-jwt}.

\par Dalam konteks HTTP, JWT sering dikirim sebagai \textit{bearer token} menggunakan header dengan nama \texttt{Authorization} dengan skema \texttt{Bearer}. Skema bearer token ini didefinisikan pada RFC 6750 dan menjadi pola umum pada layanan API modern karena sederhana dan sesuai untuk request yang \textit{stateless} \cite{rfc6750-bearer}. Dengan mekanisme ini, server dapat memverifikasi signature JWT, membaca klaim yang diperlukan (misalnya \texttt{id} dan \texttt{role}), lalu menentukan apakah request berhak mengakses endpoint tertentu. JWT juga biasanya memiliki masa berlaku (misalnya klaim \texttt{exp}) untuk membatasi risiko penyalahgunaan token \cite{rfc7519-jwt}.

\subsection{Hoppscotch API Documentation Tool}

\par Hoppscotch adalah \textit{API development ecosystem} berbasis web yang dapat digunakan untuk menguji dan mendokumentasikan endpoint API. Tool ini memudahkan pengguna dalam menyusun request (method, URL, header, dan body), melihat response (status code, header, dan payload JSON), serta melakukan iterasi pengujian dengan cepat \cite{hoppscotch-docs}.

\par Dalam pengujian REST API, Hoppscotch menyediakan fitur \textit{collections} untuk mengelompokkan request, \textit{environment variables} untuk menyimpan nilai yang sering dipakai (contoh: \textit{base URL} dan token), serta dukungan skrip (\textit{pre/post-request}) untuk otomatisasi sederhana seperti menyimpan token dari response login. Selain itu, request yang sudah disusun dapat diekspor sebagai file JSON sehingga pengujian dan dokumentasi dapat direplikasi secara konsisten \cite{hoppscotch-docs,hoppscotch-github}.

\subsection{Docker}

\par Docker adalah platform \textit{containerization} yang digunakan untuk mengembangkan, mengirim, dan menjalankan aplikasi di dalam lingkungan terisolasi yang disebut \textit{container}. Berbeda dengan pendekatan virtualisasi tradisional yang menggunakan \textit{virtual machine} (VM), Docker memanfaatkan teknologi virtualisasi tingkat sistem operasi sehingga container dapat berjalan lebih ringan, cepat, dan efisien dalam penggunaan sumber daya \cite{docker-docs}.

\par Pada arsitekturnya, Docker terdiri dari beberapa komponen utama, yaitu \textit{Docker Engine} sebagai layanan utama yang mengelola container, \textit{Docker Image} sebagai template read-only untuk membuat container, serta \textit{Docker Container} sebagai instansi yang berjalan dari sebuah image. Image biasanya dibangun menggunakan berkas \texttt{Dockerfile} yang berisi instruksi untuk menyusun lingkungan aplikasi, seperti sistem operasi dasar, dependensi, serta konfigurasi yang diperlukan \cite{docker-docs}.

\par Salah satu keunggulan utama Docker adalah portabilitas, di mana aplikasi yang telah dikemas dalam container dapat dijalankan secara konsisten di berbagai lingkungan, baik pada komputer lokal, server, maupun layanan cloud tanpa perlu konfigurasi ulang yang kompleks. Hal ini dimungkinkan karena seluruh dependensi aplikasi telah dibungkus dalam container tersebut \cite{docker-docs}.

\par Selain itu, Docker mendukung konsep \textit{image layering} dan \textit{caching} yang membuat proses build menjadi lebih efisien, serta memudahkan distribusi melalui \textit{container registry} seperti Docker Hub. Dalam praktik pengembangan modern, Docker sering digunakan bersama dengan alat orkestrasi seperti Kubernetes untuk mengelola deployment aplikasi dalam skala besar \cite{docker-docs}.

\par Dalam konteks praktikum ini, Docker digunakan untuk menjalankan layanan backend dan database secara terisolasi di dalam container pada VPS. Dengan pendekatan ini, proses instalasi, konfigurasi, dan deployment menjadi lebih sederhana serta mengurangi potensi konflik dependensi antar aplikasi.

\section{Hasil dan Pembahasan}

\par Pada pertemuan ini saya melakukan implementasi \textit{deployment} REST API berbasis PHP (JWT) menggunakan Docker pada server VPS. Alur praktikum mengikuti urutan pada modul (bagian Langkah Percobaan), dimulai dari mengecek dokumentasi resmi Docker, menginstal Docker Engine, menyiapkan folder kerja dan \textit{source code}, melakukan penyesuaian konfigurasi aplikasi agar siap dijalankan melalui Apache di dalam container, membangun Docker Image, menjalankan container, hingga menguji endpoint REST API menggunakan Hoppscotch. Selain itu, saya melakukan \textit{troubleshooting} saat koneksi MySQL dari container mengalami kegagalan, lalu memperbaiki akses user database agar dapat diakses dari jaringan. Pada akhir praktikum, saya juga mengerjakan Tugas \& Analisis yang diberikan (dibahas di bagian akhir Hasil dan Pembahasan).

\par Secara ringkas, langkah yang saya lakukan adalah sebagai berikut:
\begin{enumerate}
  \item Mengecek dokumentasi resmi instalasi Docker Engine untuk Ubuntu.
  \item Menginstal Docker Engine di VPS dan memverifikasi statusnya.
  \item Menambahkan user non-root ke grup Docker agar dapat menjalankan Docker tanpa \texttt{sudo}.
  \item Membuat folder baru di home directory dan menyalin \textit{source code} API JWT (kode lama).
  \item Mengonfigurasi koneksi database MySQL pada file \texttt{config/database.php} (\textit{hardcode}, tanpa \texttt{.env}), agar lebih mudah.
  \item Menjalankan aplikasi menggunakan PHP development server untuk memastikan API dapat diakses.
  \item Mengubah environment Hoppscotch agar \textit{base URL} mengarah ke IP VPS, lalu menguji endpoint \texttt{Cek}.
  \item Menambahkan konfigurasi \texttt{.htaccess} dan router \texttt{index.php} agar endpoint API dapat diakses dengan URL yang lebih rapi.
  \item Memperbaiki path \texttt{include/require} menggunakan konstanta \texttt{\_\_DIR\_\_}.
  \item Membuat \texttt{Dockerfile}, melakukan build image, dan menjalankan container pada port \texttt{8000}.
  \item Menyesuaikan kembali base URL Hoppscotch agar sesuai dengan base path saat aplikasi berjalan di container.
  \item Melakukan \textit{troubleshooting} koneksi MySQL dari container dengan menambahkan user ke database yang dapat diakses dari semua host.
  \item Menguji endpoint \texttt{Login} dan \texttt{Get All Users} pada aplikasi yang berjalan di Docker.
  \item Mengerjakan Tugas \& Analisis (dibahas di bagian akhir Hasil dan Pembahasan).
\end{enumerate}

sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt-get update
sudo apt-get install -f
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
\end{lstlisting}

\begin{lstlisting}[caption={Konfigurasi koneksi database pada kode baru (\texttt{config/database.php})}, label={lst:db-config-hardcode}]
<?php
// used to get mysql database connection
class DatabaseService{

    private $db_host = "10.33.35.96";
    private $db_port = 3306;
    private $db_name = "sait_db";
    private $db_user = "fauzan";
    private $db_password = "fauzan123";

        $this->connection = null;

        try{
            $this->connection = new PDO("mysql:host=" . $this->db_host . ";port=" . $this->db_port . ";dbname=" . $this->db_name, $this->db_user, $this->db_password);
        }catch(PDOException $exception){
            echo "Connection failed: " . $exception->getMessage();
        }

        return $this->connection;
    }
}

  \includegraphics[width=0.95\textwidth]{resource/Dokumentasi/18 - edit htaccess.png}

  \label{fig:p9-18-htaccess}
\end{figure}

\par Selain itu, file \texttt{index.php} di root project diubah menjadi router sederhana agar request ke endpoint seperti \texttt{/api/login} atau \texttt{/api/users} dapat diarahkan ke file handler yang sesuai. Perubahan router di root ditunjukkan pada Gambar \ref{fig:p9-19-router-index}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{resource/Dokumentasi/19 - edit index.php di root agar ada helper untuk api.png}
  \caption{Mengubah \texttt{index.php} di root menjadi router untuk endpoint API}
  \label{fig:p9-19-router-index}
\end{figure}

\par Cuplikan konfigurasi \texttt{.htaccess} dan router \texttt{index.php} ditunjukkan pada Kode \ref{lst:htaccess} dan Kode \ref{lst:router-index}.

\begin{lstlisting}[caption={Konfigurasi \texttt{.htaccess} pada kode baru}, label={lst:htaccess}]
<IfModule mod_rewrite.c>
    DirectorySlash Off
    RewriteEngine On
    RewriteCond %{HTTP:Authorization} ^(.*)
    RewriteRule .* - [e=HTTP_AUTHORIZATION:%1]
    RewriteCond %{REQUEST_FILENAME} !-f
    RewriteRule ^ index.php [L]
</IfModule>
\end{lstlisting}

\begin{lstlisting}[caption={Router sederhana pada root project (\texttt{index.php})}, label={lst:router-index}]
<?php
// CORS headers
header("Access-Control-Allow-Origin: *");
header("Content-Type: application/json; charset=UTF-8");
header("Access-Control-Allow-Methods: POST, GET, OPTIONS");
header("Access-Control-Max-Age: 3600");
header("Access-Control-Allow-Headers: Content-Type, Access-Control-Allow-Headers, Authorization, X-Requested-With");

// Handle preflight request
if ($_SERVER['REQUEST_METHOD'] === 'OPTIONS') {
    http_response_code(200);
    exit();
}

// Normalize URI
$requestUri = $_SERVER['REQUEST_URI'];
$requestUri = strtok($requestUri, '?');

if ($requestUri !== '/' && substr($requestUri, -1) === '/') {
    $requestUri = rtrim($requestUri, '/');
}

// Routing
switch ($requestUri) {

    case '/api/login':
        require 'api/login/index.php';
        break;

    case '/api/register':
        require 'api/register/index.php';
        break;

    case '/api/users':
        require 'api/users/index.php';
        break;

    case '/':
    case '/index.php':
        http_response_code(200);
        echo json_encode(["message" => "Welcome to the API service"]);
        break;

    default:
        http_response_code(404);
        echo json_encode([
            "message" => "Endpoint not found.",
            "debug_uri" => $requestUri
        ]);
        break;
}
?>
\end{lstlisting}

\par Dari kode diatas \ref{lst:htaccess} dan \ref{lst:router-index} terlihat bahwa \texttt{.htaccess} mengaktifkan rewrite dan memastikan header \texttt{Authorization} diteruskan ke PHP, sedangkan \texttt{index.php} berfungsi sebagai router yang memeriksa URI request dan mengarahkan ke file handler yang sesuai untuk setiap endpoint API. Dengan konfigurasi ini, aplikasi siap dijalankan di Apache dalam container Docker nanti.
\par dengan begitu, enpoint API tidak perlu mencantumkan path dengan index.php, sehingga URL menjadi lebih rapi seperti \texttt{/api/login} daripada \texttt{/index.php/api/login}. Padahal di praktikum sebelumnya, endpoint API harus saya akses dengan menyertakan \texttt{index.php} di URL karena belum ada router yang menangani request secara dinamis. Dengan adanya router di root, maka semua request dapat diarahkan ke file handler yang sesuai tanpa perlu menyertakan \texttt{index.php} di URL, sehingga lebih bersih dan mudah diingat.

\subsection{Perbaikan Path Import Menggunakan \texttt{\_\_DIR\_\_}}
\par Setelah router digunakan, eksekusi file endpoint tidak selalu berada pada working directory yang sama, sehingga relative path seperti \texttt{../../config/database.php} dan \texttt{../../vendor/autoload.php} berpotensi gagal ditemukan. Untuk mengatasi hal ini, saya mengubah import file pada endpoint menjadi berbasis \texttt{\_\_DIR\_\_} (Gambar \ref{fig:p9-20-dir-require}) sehingga path selalu dihitung dari lokasi file itu sendiri.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{resource/Dokumentasi/20 - mengedit require path menggunakan dir, disitu ada kelasalah dan di perbaiki setelah di screnshoot tentang tanda slash di setelag titik setelah dir.png}
  \caption{Perbaikan \texttt{include/require} menggunakan konstanta \texttt{\_\_DIR\_\_}}
  \label{fig:p9-20-dir-require}
\end{figure}

\par Sebetulnya pada gambar \ref{fig:p9-20-dir-require} terlihat bahwa pada awalnya saya lupa menambahkan tanda slash (/) setelah \texttt{\_\_DIR\_\_}, sehingga path yang dihasilkan menjadi salah (misalnya \texttt{/var/www/htmlapi/login/../../config/database.php} yang tidak valid). Setelah diperbaiki dengan menambahkan slash, path jadi bisa berfungsi dengan benar (misalnya \texttt{/var/www/html/api/login/../../config/database.php}) dan file dapat ditemukan dengan benar.

\par Contoh perubahan import pada endpoint \texttt{/api/users/index.php} ditunjukkan pada Kode \ref{lst:dir-snippet}.

\begin{lstlisting}[caption={Cuplikan perubahan import menggunakan \texttt{\_\_DIR\_\_}}, label={lst:dir-snippet}]
/* Sebelum */
include_once '../../config/database.php';
require "../../vendor/autoload.php";

/* Sesudah */
include_once __DIR__ . '/../../config/database.php';
require __DIR__ . "/../../vendor/autoload.php";
\end{lstlisting}

\par Dengan perubahan tersebut, maka file yang diimport akan selalu dihitung relatif terhadap lokasi file endpoint itu sendiri, sehingga tidak tergantung pada working directory saat aplikasi dijalankan. Hal ini sangat penting agar aplikasi dapat berjalan dengan benar baik saat dijalankan secara langsung maupun di dalam container Docker nanti.

\par Ringkasnya, \texttt{Dockerfile} menggunakan base image \texttt{php:8.2-apache}, menginstal ekstensi \texttt{pdo\_mysql} untuk koneksi database, mengaktifkan modul \texttt{rewrite} dan \texttt{headers}, mengizinkan \texttt{.htaccess} dibaca (\texttt{AllowOverride All}), lalu mengganti port Apache dari \texttt{80} menjadi \texttt{8000}. \begin{lstlisting}[caption={Isi \texttt{Dockerfile} pada kode baru}, label={lst:dockerfile}]
FROM php:8.2-apache

RUN docker-php-ext-install pdo_mysql

RUN a2enmod rewrite headers

RUN sed -ri 's/AllowOverride None/AllowOverride All/g' /etc/apache2/apache2.conf

RUN rm -f /var/www/html/index.html

RUN sed -ri 's/Listen 80/Listen 8000/g' /etc/apache2/ports.conf \
    && sed -ri 's/:80>/:8000>/g' /etc/apache2/sites-available/000-default.conf

WORKDIR /var/www/html

COPY . /var/www/html

EXPOSE 8000

CMD ["apache2-foreground"]
\end{lstlisting}

\subsubsection{Bagaimana cara menghapus Docker Image/Container yang telah dibuat?}
\par Untuk menghapus container yang sedang berjalan, langkahnya adalah menghentikan container lalu menghapusnya. Setelah container dihapus, image dapat dihapus menggunakan \texttt{docker rmi}. Pada praktikum ini, contoh alur penghapusan/recreate container ditunjukkan pada Gambar \ref{fig:p9-32-task}.

\begin{lstlisting}[caption={Contoh menghapus container dan image Docker}, label={lst:docker-remove}]
docker ps
docker stop jwt-app
docker rm jwt-app

docker images
docker rmi jwt-pertemuan-8-9
\end{lstlisting}

\subsubsection{Bagaimana jika source code berubah dan Image/Container ingin diperbarui?}
\par Jika source code berubah, image perlu dibangun ulang dengan \texttt{docker build}. Apabila ingin menggunakan nama container yang sama, container lama harus dihentikan dan dihapus terlebih dahulu agar tidak terjadi konflik nama. Pada praktikum ini, saya sempat mendapatkan error konflik nama container \texttt{jwt-app} sehingga perlu melakukan \texttt{docker stop} dan \texttt{docker rm} sebelum menjalankan container kembali. \section{Kesimpulan}

\par Kesimpulan dari praktikum \textit{API PHP dengan Docker} adalah sebagai berikut:
\begin{enumerate}
  \item Docker Engine berhasil diinstal pada Ubuntu VPS dan terverifikasi berjalan aktif melalui \texttt{systemctl status docker} serta pengujian \texttt{docker run hello-world}.
  \item Aplikasi REST API PHP (JWT) berhasil dipersiapkan dari \textbf{kode lama} menjadi \textbf{kode baru} dengan penambahan konfigurasi \texttt{.htaccess}, router \texttt{index.php}, serta perbaikan import path menggunakan \texttt{\_\_DIR\_\_}.
  \item \texttt{Dockerfile} berhasil dibuat dan disesuaikan menggunakan port \texttt{8000}, kemudian image \texttt{jwt-pertemuan-8-9} berhasil dibangun dan dijalankan sebagai container.
  \item Hoppscotch mempermudah pengujian endpoint karena base URL dapat disimpan sebagai environment variable dan request dapat dieksekusi berulang tanpa menulis ulang URL.
  \item Kendala utama yang ditemui adalah kegagalan koneksi MySQL dari container (\texttt{Connection refused}). Masalah ini diselesaikan dengan menambahkan user MySQL yang dapat diakses dari semua host (\texttt{\%}) dan memberikan hak akses ke database \texttt{sait\_db}.
  \item Pengelolaan image/container dapat dilakukan dengan menghentikan dan menghapus container lama, lalu membangun ulang image dan menjalankan container baru ketika source code mengalami perubahan.
\end{enumerate}
