\section{Tujuan Praktikum}
\begin{enumerate}
  \item Mahasiswa mampu melakukan replikasi database menggunakan MySQL.
  \item Dapat menyelesaikan kasus tidak terreplikanya database yang sudah ada sebelum replikasi dijalankan.
\end{enumerate}

\section{Dasar Teori}
\subsection{MySQL}

\par MySQL adalah sistem manajemen basis data relasional (RDBMS) yang menggunakan Structured Query Language (SQL) untuk melakukan definisi skema, manipulasi data, dan query. MySQL menerapkan arsitektur client--server, di mana proses server (\texttt{mysqld}) menyimpan serta mengelola data, sedangkan klien (misalnya \texttt{mysql}) digunakan untuk terhubung dan mengeksekusi perintah SQL. Dalam praktik pengembangan aplikasi, MySQL banyak dipakai karena performanya baik, dukungan ekosistem luas, serta ketersediaan dokumentasi yang lengkap \cite{mysql-refman}.

\par Pada sisi administrasi sistem, konfigurasi MySQL umumnya dilakukan melalui berkas konfigurasi (misalnya \texttt{mysqld.cnf} di Linux atau \texttt{my.ini} di Windows) untuk mengatur parameter layanan seperti port, direktori data, serta kebijakan akses jaringan melalui \texttt{bind-address}. Selain itu, MySQL memiliki mekanisme autentikasi dan hak akses (privileges) untuk memastikan hanya user tertentu yang dapat mengakses database sesuai perannya \cite{mysql-refman}.

\subsection{Replika}

\par Replikasi database MySQL adalah mekanisme penyalinan perubahan data dari server sumber (source/master) ke server replika (replica/slave) secara otomatis. Pada replikasi berbasis binary log, setiap perubahan pada source dicatat sebagai event pada binary log, lalu replica membaca event tersebut dan mengeksekusinya sehingga data tetap konsisten. Konsep ini sering dimanfaatkan untuk kebutuhan redundansi (cadangan), distribusi beban baca (read scaling), serta pemulihan ketika terjadi kegagalan pada server utama \cite{mysql-replication,mysql-binary-log}.

\par Secara umum, replikasi memerlukan beberapa prasyarat: source harus mengaktifkan binary log (\texttt{log\_bin}) dan setiap server harus memiliki \texttt{server-id} yang unik. Replica kemudian dikonfigurasi untuk terhubung ke source menggunakan koordinat replikasi (misalnya \textit{file/position} dari \texttt{SHOW MASTER STATUS}) dan kredensial user replikasi. Pada MySQL 8, konfigurasi dapat dilakukan menggunakan perintah \texttt{CHANGE REPLICATION SOURCE TO} (atau \texttt{CHANGE MASTER TO} pada istilah lama), lalu replikasi dijalankan dengan \texttt{START REPLICA/SLAVE} dan dipantau melalui \texttt{SHOW REPLICA/SLAVE STATUS} \cite{mysql-replication,mysql-change-replication-source-to}.

\section{Hasil dan Pembahasan}

\par Pada pertemuan kali ini saya melakukan konfigurasi replikasi database MySQL antara Ubuntu Server sebagai \textit{Master} dan komputer Windows sebagai \textit{Slave}. Replikasi digunakan agar perubahan data pada database di Master dapat disalin secara otomatis ke database di Slave sebagai cadangan (\textit{redundancy}) dan untuk kebutuhan uji coba.

\par Secara ringkas, langkah-langkah yang saya lakukan adalah sebagai berikut:
\begin{enumerate}
  \item Menyiapkan MySQL Community Server (portable ZIP) pada komputer Slave (Windows) beserta file konfigurasi \texttt{my.ini}.
  \item Mengaktifkan pengaturan replikasi pada MySQL Master (Ubuntu Server) dengan mengubah \texttt{bind-address}, \texttt{server-id}, dan \texttt{log\_bin}.
  \item Membuat user khusus replikasi di Master dan memberikan privilege \texttt{REPLICATION SLAVE}.
  \item Mengambil posisi \textit{binary log} di Master (\texttt{MASTER\_LOG\_FILE} dan \texttt{MASTER\_LOG\_POS}) untuk acuan konfigurasi Slave.
  \item Menghubungkan Slave ke Master menggunakan perintah \texttt{CHANGE MASTER TO} lalu menjalankan replikasi dan memverifikasi statusnya.
  \item Menguji replikasi dengan membuat database baru di Master dan memastikan database tersebut muncul di Slave.
  \item Menganalisis perbedaan jumlah database (Master memiliki 6 database sedangkan Slave 5 database) dan menerapkan solusi agar database \texttt{sait\_db} ikut tersalin dan tetap tereplikasi.
  \item Menjelaskan implementasi backend (\texttt{resource/new}) dan frontend (\texttt{resource/fe\_new}) yang digunakan sebagai aplikasi uji (\textit{CRUD}) pada database.
\end{enumerate}

\subsection{Menyiapkan MySQL pada Komputer Slave (Windows)}
\par Pada sisi komputer (Windows) saya menggunakan MySQL Community Server versi ZIP (portable). Berbeda dengan Ubuntu yang dapat dijalankan sebagai service, pada Windows portable MySQL dijalankan melalui command prompt dan memerlukan file konfigurasi \texttt{my.ini} agar port dan folder data terset dengan benar.

\par Konfigurasi dasar yang saya gunakan pada \texttt{my.ini} mencakup port non-standar (\texttt{3333}) serta lokasi \texttt{basedir} dan \texttt{datadir}. Setelah itu (sebelum replikasi) saya menambahkan \texttt{server-id=2} agar unik (berbeda dengan Master). Contoh struktur konfigurasi dapat dilihat pada Kode \ref{lst:myini-slave}.
\begin{lstlisting}[caption={Contoh konfigurasi \texttt{my.ini} pada MySQL Slave (Windows)}, label={lst:myini-slave}]
[mysqld]
port=3333

# Sesuaikan path dengan folder hasil ekstrak MySQL di komputer masing-masing
# Gunakan garis miring (/) agar aman
basedir=D:/path/to/mysql-8.0.xx-winx64
datadir=D:/path/to/mysql-8.0.xx-winx64/data

server-id=2

# Optional: untuk mengurangi beban (hanya untuk simulasi)
innodb_buffer_pool_size = 64M
performance_schema = 0
mysqlx = 0
max_connections = 20
\end{lstlisting}

\par Setelah konfigurasi dibuat, proses yang saya lakukan pada Windows adalah melakukan inisialisasi direktori data, menjalankan server MySQL, dan masuk ke MySQL CLI dengan port \texttt{3333}. Perintah yang digunakan ditunjukkan pada Kode \ref{lst:cmd-windows-mysql}.
\begin{lstlisting}[caption={Inisialisasi dan menjalankan MySQL portable pada Windows (Slave)}, label={lst:cmd-windows-mysql}]
cd D:\path\to\mysql-8.0.xx-winx64\bin

mysqld --defaults-file=my.ini --initialize-insecure --console
mysqld --console

mysql -u root -P 3333
\end{lstlisting}

\subsection{Mengonfigurasi MySQL Master (Ubuntu Server)}
\par Pada sisi server (Ubuntu) saya mengubah konfigurasi MySQL agar dapat diakses dari jaringan (tidak hanya \textit{localhost}) dan mengaktifkan \textit{binary log} sebagai syarat replikasi. File konfigurasi yang diubah adalah \texttt{/etc/mysql/mysql.conf.d/mysqld.cnf}.

\par Perintah untuk mengedit konfigurasi dan melakukan restart service ditunjukkan pada Kode \ref{lst:cmd-ubuntu-config-master}.
\begin{lstlisting}[caption={Mengedit konfigurasi MySQL Master (Ubuntu Server)}, label={lst:cmd-ubuntu-config-master}]
sudo nano /etc/mysql/mysql.conf.d/mysqld.cnf
sudo systemctl restart mysql
\end{lstlisting}

\par Bagian konfigurasi yang menjadi kunci pada Master adalah \texttt{bind-address=0.0.0.0} (agar bisa menerima koneksi dari luar), \texttt{server-id=1} (identitas Master), dan \texttt{log\_bin} (aktifkan binary logging). Cuplikan konfigurasi ditunjukkan pada Kode \ref{lst:mysqldcnf-master}.
\begin{lstlisting}[caption={Cuplikan konfigurasi penting \texttt{mysqld.cnf} pada Master}, label={lst:mysqldcnf-master}]
# Akses jaringan
bind-address = 0.0.0.0

# Identitas server untuk replikasi
server-id = 1

# Aktifkan binary log
log_bin = /var/log/mysql/mysql-bin.log
\end{lstlisting}

\subsection{Membuat User Replikasi di Master}
\par Agar MySQL Slave dapat mengambil data dari Master, saya membuat user khusus replikasi dan memberikan hak akses \texttt{REPLICATION SLAVE}. Pembuatan user dilakukan di MySQL CLI pada Ubuntu Server. Perintah SQL yang digunakan ditunjukkan pada Kode \ref{lst:sql-create-repl-user}.
\begin{lstlisting}[caption={Membuat user replikasi pada Master dan memberikan privilege}, label={lst:sql-create-repl-user}]

GRANT REPLICATION SLAVE ON *.* TO 'replica_user'@'%';
FLUSH PRIVILEGES;
\end{lstlisting}

\subsection{Menghubungkan Slave ke Master dan Menjalankan Replikasi}
\par Pada sisi komputer Slave (Windows), saya menghubungkan MySQL Slave ke Master menggunakan perintah \texttt{CHANGE MASTER TO} dengan parameter host Master, user replikasi, serta nilai \texttt{MASTER\_LOG\_FILE} dan \texttt{MASTER\_LOG\_POS} yang didapatkan dari langkah sebelumnya.

\par Konfigurasi koneksi replikasi di MySQL Slave ditunjukkan pada Kode \ref{lst:sql-change-master}. Pada praktik ini, Master menggunakan port default \texttt{3306}, sedangkan server MySQL di Windows dijalankan pada port \texttt{3333}.
\begin{lstlisting}[caption={Menghubungkan Slave ke Master menggunakan \texttt{CHANGE MASTER TO}}, label={lst:sql-change-master}]
CHANGE MASTER TO
  MASTER_HOST='10.33.35.96',
  MASTER_USER='replica_user',
  MASTER_PASSWORD='abc',
  MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=157;

START REPLICA; -- atau START SLAVE;
\end{lstlisting}

\par Setelah replikasi dijalankan, status replikasi diperiksa menggunakan \texttt{SHOW SLAVE STATUS\textbackslash G} (atau \texttt{SHOW REPLICA STATUS\textbackslash G} pada MySQL versi baru). Indikator yang diperhatikan adalah \texttt{Slave\_IO\_Running} dan \texttt{Slave\_SQL\_Running} yang keduanya harus bernilai \texttt{Yes}.

\subsection{Analisis: Mengapa \texttt{sait\_db} Tidak Tereplikasi ke Slave}
\par Dari hasil pengecekan, jumlah database pada Master lebih banyak dibandingkan Slave. Master memiliki 6 database, sedangkan Slave hanya memiliki 5 database. Database yang tidak muncul di Slave adalah \texttt{sait\_db}.

\par Penyebab utama \texttt{sait\_db} tidak ikut muncul di Slave adalah karena replikasi MySQL berbasis \textit{binary log} hanya mengirimkan \textit{perubahan} setelah Slave mulai membaca dari posisi tertentu (\texttt{MASTER\_LOG\_FILE} dan \texttt{MASTER\_LOG\_POS}). Jika \texttt{sait\_db} sudah ada dan sudah terisi data \textbf{sebelum} proses replikasi dimulai, maka event \texttt{CREATE DATABASE} dan data awalnya tidak lagi dikirim ke Slave (karena event tersebut berada \textit{sebelum} posisi replikasi yang digunakan). Akibatnya, database tersebut tidak otomatis tersalin ke Slave.

\par Hal ini terlihat dari cuplikan dump SQL \texttt{all.sql} (hasil \textit{backup}) yang memuat pembuatan database \texttt{sait\_db} dan data tabel \texttt{mahasiswa}. Agar dokumen tidak terlalu panjang, saya menampilkan cuplikan kecil yang diambil dari \texttt{all.sql} pada Kode \ref{lst:allsql-saitdb-excerpt}.

\subsection{Solusi: Menyalin \texttt{sait\_db} ke Slave dan Menjaga Replikasi Tetap Berjalan}
\par Solusi yang dilakukan agar \texttt{sait\_db} ikut ada di Slave dan selanjutnya ikut tereplikasi ketika ada penambahan data adalah melakukan \textit{sinkronisasi awal} (\textit{initial seeding}) database tersebut dari Master ke Slave. Secara umum terdapat dua pendekatan:
\begin{enumerate}
  \item \textbf{Dump hanya database \texttt{sait\_db}} lalu import ke Slave (lebih aman dan ukuran file lebih kecil).
  \item \textbf{Dump seluruh database} (\texttt{--all-databases}) lalu import ke Slave. Pada praktik nyata, pendekatan ini perlu hati-hati karena dapat menimpa database sistem \texttt{mysql} (privilege).
\end{enumerate}

\par Pada praktikum ini saya menggunakan dump SQL sebagai sumber penyalinan awal (contohnya \texttt{all.sql}). Langkah solusi yang dapat dilakukan adalah sebagai berikut:
\begin{enumerate}
  \item \textbf{(Slave/Windows)} Hentikan replikasi sementara untuk mencegah konflik saat import: \texttt{STOP SLAVE;} / \texttt{STOP REPLICA;}.
  \item \textbf{(Master/Ubuntu)} Buat dump database \texttt{sait\_db}: \texttt{mysqldump --databases sait\_db > sait\_db.sql} (atau gunakan \texttt{all.sql} yang sudah dibuat).
  \item \textbf{(Transfer)} Pindahkan file dump (\texttt{sait\_db.sql} atau \texttt{all.sql}) ke komputer Slave.
  \item \textbf{(Slave/Windows)} Import dump ke MySQL Slave melalui command prompt (bukan di dalam MySQL CLI) dan pastikan port sesuai, misalnya \texttt{-P 3333}.
  \item \textbf{(Slave/Windows)} Jalankan kembali replikasi, lalu cek status replikasi sampai proses I/O dan SQL berjalan (running) dan tidak ada error.
  \item \textbf{(Uji)} Tambahkan data baru pada \texttt{sait\_db} di Master (misal insert ke tabel \texttt{mahasiswa}) lalu verifikasi data tersebut muncul di Slave.
\end{enumerate}

\par Contoh perintah dump dan import yang digunakan ditunjukkan pada Kode \ref{lst:cmd-dump-import-saitdb}. Perintah ini juga menjelaskan perbedaan konteks: dump dilakukan pada sisi server (Ubuntu Master) sedangkan import dilakukan pada sisi komputer (Windows Slave).
\begin{lstlisting}[caption={Contoh perintah dump dan import \texttt{sait\_db} (Master vs Slave)}, label={lst:cmd-dump-import-saitdb}]
# (Ubuntu Master) dump database sait_db saja
sudo mysqldump --databases sait_db --single-transaction > sait_db.sql

# (Windows Slave) import ke MySQL slave (jalankan di CMD/PowerShell, bukan di mysql>)
D:\path\to\mysql\bin\mysql -u root -P 3333 < "D:\path\to\sait_db.sql"

# (Windows Slave) jalankan kembali replikasi
START SLAVE;
SHOW SLAVE STATUS\G
\end{lstlisting}

\par Pada sisi Master, proses dump harus dijalankan di shell (bukan di dalam prompt \texttt{mysql>}). Selain itu, pada Ubuntu sering kali user \texttt{root} menggunakan autentikasi \textit{socket}, sehingga \texttt{mysqldump -u root -p} dapat memunculkan error akses (contohnya ditunjukkan pada Gambar \ref{fig:p6-17-mysqldump-master}). Salah satu solusi yang umum adalah menggunakan \texttt{sudo mysqldump ...} atau membuat user khusus backup.

\section{Kesimpulan}

\par Kesimpulan dari praktikum replikasi database MySQL adalah sebagai berikut:
\begin{enumerate}
  \item Replikasi database menggunakan MySQL antara Master (Ubuntu Server) dan Slave (Windows) berhasil dikonfigurasi dan dijalankan. Hal ini dibuktikan dengan database yang dibuat di Master serta perubahan data yang dilakukan dapat muncul dan sinkron di Slave setelah replikasi aktif.
  \item Kasus tidak tereplikanya database yang sudah ada sebelum replikasi dijalankan terjadi karena mekanisme replikasi berbasis binary log hanya menerapkan event setelah posisi log tertentu (\textit{file/position}) yang dijadikan titik awal. Solusinya adalah melakukan \textit{initial seeding} dengan menyalin data awal (misalnya melalui \texttt{mysqldump} dan import) ke Slave, lalu menjalankan kembali replikasi agar perubahan berikutnya tetap tersalin otomatis, termasuk pada database \texttt{sait\_db}.
\end{enumerate}
